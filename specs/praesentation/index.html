Teil 1 · Kontext

Was ist CaseFlow?

Ein Case-Management-Tool für Case Manager der CSS. Fälle werden erfasst, zugewiesen, bearbeitet und abgeschlossen — an einem Ort statt in E-Mail und Excel.

Alles an einem Ort

Erfassung bis Abschluss ohne Systemwechsel.

Keine verpassten Fristen

Wiedervorlagen & Fälligkeiten aktiv nachverfolgt.

Lückenlose Spur

Jede Statusänderung im Audit-Trail belegbar.

Technisch: ein Quarkus Backend-for-Frontend, das eine Angular-SPA ausliefert — ein Maven-Modul.

Fachlicher Kontext in einem Satz: Case Manager jonglieren heute E-Mail, Excel und Kernsystem — Faelle gehen unter, Fristen (KVG/VVG) werden knapp. CaseFlow bringt das an einen Ort. Wichtig fuer spaeter: der Audit-Trail ist fachliche Anforderung, kein Logging — jede Statusaenderung muss belegbar sein. Gesundheitsdaten sind besonders schuetzenswert.
Teil 1 · Ausgangslage

Fundament steht — Backlog offen

Die ersten Use Cases sind vollständig umgesetzt — das Case-Aggregat existiert samt Persistenz, REST und Tests:

  • US-1 Fall erfassen — POST /api/v1/cases
  • US-2 Fall zuweisen — PUT /api/v1/cases/{id}/assignment
  • plus /api/v1/me, /api/v1/version & App-Shell

Offen: US-3 … US-9 (bearbeiten, Fristen, Abschluss, Übersicht, Audit).

Case.java · CaseResource.java

Warum das ideal ist

US-1 und US-2 sind das Referenzmuster: jede Story ist eine vollständige vertikale Schicht — Domain → Persistence → REST → Frontend → Migration → Tests.

Die offenen Stories lassen sich an diesem Muster üben — der volle SDD-Fluss immer wieder komplett.

Wichtig zu betonen: Das Projekt ist KEIN leeres Skelett mehr — US-1 (Fall erfassen) und US-2 (Fall zuweisen) sind real umgesetzt, inkl. Case-Aggregat, Panache-Persistenz, REST und Cucumber-Features. Diese zwei sind das lebende Referenzbeispiel, an dem sich US-3 bis US-9 orientieren. Genau deshalb eignet sich das Repo als Uebungsobjekt: es gibt ein Vorbild UND offenen Backlog zum Selbermachen.

Teil 1 · Architektur

Hexagonal wo · DDD welche Form

Ports & Adapters für die Gesamtstruktur, taktisches DDD im inneren Hexagon.

  • domain/ — reine Business-Logik, null Framework-Imports
  • application/ — Use-Case-Orchestrierung, Transaktionsgrenze
  • adapter/in/rest/ — Driving Adapters (JAX-RS)
  • adapter/out/persistence/ — Driven Adapters (Panache)

Abhängigkeiten zeigen immer nach innen.

DDD-Bausteine

CaseAggregate Root
PriorityValue Object (record)
CaseAssignedDomain Event
CaseRepositoryDriven Port
CreateCaseServiceApplication Service

Domänenmodelle sind immutable Records. Audit-Trail ist Teil der Domäne.

Merksatz: Hexagonal sagt WO Code lebt, DDD sagt WELCHE FORM er hat. Die wichtigste Regel: domain/ hat null Framework-Imports — das wird per ArchUnit erzwungen (kommt zwei Folien spaeter). Aggregate referenzieren einander per ID, nicht per Objektreferenz. Application Service orchestriert, Domain Service haelt Logik — nicht vermischen.
Teil 1 · Kernidee

Der Spec-Driven-Fluss

/taskIssue
→
/planPlan
→
/implementCode + Tests + .feature
→
Reviewer-Agenten
→
/shipPR → Merge

Jede Änderung hinterlässt eine nachvollziehbare Spur.

Issue → Spec → Plan → Code + Tests → PR. Kurzformen: /fast = task+plan+implement, /autoship = alles inkl. Merge.

Das ist die zentrale Folie. Jeder Schritt erzeugt ein reales Artefakt im Repo — kein Prozess auf Folien, sondern Dateien. Plan-Gate erwaehnen: bei nicht-trivialen Issues (mehr als 3 Akzeptanzkriterien, mehrere Schichten, Migration/Auth/Audit) ist ein bestaetigter Plan Pflicht. Kurzformen /fast und /autoship nur kurz nennen.

Teil 1 · Aha-Moment

Specs, die laufen

In der User Story

### Szenario 1: Fall erfassen (Happy Path)
- Gegeben sei ein angemeldeter CASE_MANAGER
- Wenn er einen Fall mit Falltyp,
  Prioritaet, Quelle, Referenz erfasst
- Dann wird der Fall im Status NEU
  gespeichert

Als .feature ausgeführt

# fall-erfassen.feature
Feature: US-1 Fall erfassen
  Szenario: Fall erfassen (Happy Path)
    Angenommen ein CASE_MANAGER
    Wenn POST /api/v1/cases ...
    Dann Status 201 und NEU

Dieselben Szenarien — einmal als Spezifikation, einmal als Test.

Live im Repo: 1-fall-erfassen.md · fall-erfassen.feature

Der Kern von SDD zum Anfassen: die fachliche Spezifikation IST der Test. Kein Uebersetzungsverlust zwischen Anforderung und Verifikation. Genau diese Kopplung haelt der SpecScenarioParityTest wach — naechste Folie. Diesen Punkt langsam machen, das ist der Aha-Moment fuer Skeptiker.
Teil 1 · Durchsetzung

Guardrails brechen den Build

Nicht erst ein Reviewer merkt Drift — der Build wird rot.

HexagonArchitectureTest

ArchUnit: Domain ohne Framework-Imports, Adapter nur nach innen.

SpecScenarioParityTest

Story und .feature müssen gleich viele Szenarien führen.

DisplayTextTransliterationTest

Keine ASCII-Transliteration (ae/ue/oe) in kundensichtbarem Text.

Wenn Spezifikation und Code auseinanderlaufen, scheitert ./mvnw verify — genau das üben wir gleich.

Kernaussage: Reviews sind fehlbar und langsam, ein roter Build ist es nicht. Diese drei Tests sind ausfuehrbare Prozessregeln. In Uebung 2 zerbrechen die Teilnehmer den SpecScenarioParityTest bewusst und heilen ihn wieder — das ist der staerkste Lernmoment des Workshops. Optional live vormachen.

Ein Hook erinnert nach Edits automatisch an den passenden Reviewer.

Diese Ebene ist optional fuer SDD, aber sie operationalisiert den Fluss mit KI-Agenten. Wichtig: Skills laufen nur auf ausdruecklichen Aufruf, nie von selbst. Die Reviewer-Agenten sind spezialisiert und werden per Hook nach den passenden Datei-Edits vorgeschlagen. Wer ohne Agenten arbeitet: der Fluss und die Guardrails funktionieren trotzdem.
Teil 2

Übungen — jetzt selbst.

Fünf Übungen mit steigendem Anspruch. Jede ist eigenständig.

Einsteiger Fortgeschritten Anspruchsvoll

Vorbereitung: Repo geklont, ./mvnw lauffähig, Container-Runtime (Docker/Podman) für ITs & Cucumber.

Kurz Setup abfragen: Wer hat das Repo geklont und mvnw lauffaehig? Wer hat eine Container-Runtime? Ohne Container laufen Uebungen 1-2 trotzdem (nur der Parity-Test braucht keinen Container), Uebung 4 braucht ihn fuer die ITs. Paare bilden lassen, falls jemand kein Setup hat.
Übung 1 · Aufwärmen

Das Repo & den Fluss verstehen

Ziel: sich im Projekt orientieren und die Artefaktkette an einem echten Beispiel nachvollziehen.

  1. Lies specs/spec-flow.md — skizziere den Fluss in eigenen Worten.
  2. Öffne die Story 1-fall-erfassen.md und folge den Links zu Issue, Plan und Feature.
  3. Finde die passende .feature-Datei und zähle die Szenarien. Stimmt die Anzahl mit der Story überein?
  4. Starte ./mvnw quarkus:dev, öffne die App und rufe /api/v1/me auf.

Ergebnis: Du kannst erklären, wie Story ↔ Plan ↔ Feature ↔ Code zusammenhängen.

Zeitbudget ~8 Minuten. Ziel ist Orientierung, nicht Vollstaendigkeit. Beim Zaehlen der Szenarien merken die Teilnehmer selbst die Parity-Regel — perfekte Ueberleitung zu Uebung 2. Wer /api/v1/me aufruft, sieht die Dev-Identitaet CASE_MANAGER (OIDC ist in dev aus).
Übung 2 · Guardrail erleben

Drift erzeugen — und heilen

Ziel: am eigenen Leib spüren, wie ein Guardrail Spec und Code synchron hält.

Brechen

  1. Füge in einer Story ein viertes BDD-Szenario hinzu — ohne die .feature anzupassen.
  2. Führe ./mvnw test -Dtest=SpecScenarioParityTest aus.
  3. Beobachte den roten Build und lies die Fehlermeldung.

Heilen

  1. Ergänze das passende Szenario in der .feature.
  2. Test erneut ausführen — jetzt grün.
  3. Bonus: brich DisplayTextTransliterationTest, indem du "Faelle" in einen Angular-Text schreibst.

Ergebnis: Du verstehst, warum Guardrails wirksamer sind als Reviews allein.

Zeitbudget ~7 Minuten. Das ist die wichtigste Uebung. Wichtig: die Aenderungen danach wieder verwerfen (git checkout .), damit das Repo sauber bleibt. Die Fehlermeldung des Parity-Tests nennt Story- und Feature-Pfad samt Zaehlung — vorlesen lassen. Der Transliterations-Bonus zeigt die Sprachregel: Umlaute in Anzeigetext Pflicht.
Übung 3 · Von der Idee zum Plan

Story lesen, Plan schreiben

Ziel: eine noch nicht umgesetzte Story analysieren und einen Implementierungsplan formulieren.

  1. Wähle eine offene Story, z. B. 3-fall-bearbeiten.md oder 4-frist-setzen.md.
  2. Identifiziere: welche Schichten sind betroffen (Domain / Application / Adapter / Frontend)?
  3. Schreibe einen Plan nach dem Muster von us-7-fall-erfassen.md: Architektur-Entscheide, zu erstellende Dateien, Test-Strategie.
  4. Prüfe gegen das Plan-Gate: >3 Akzeptanzkriterien, mehrere Schichten, Migration/Auth/Audit → Plan Pflicht.

Tipp: Referenziere jede Aufgabe zurück auf ein Akzeptanzkriterium — Traceability von Anfang an.

Zeitbudget ~10 Minuten. Wer den Skill /plan nutzt, laesst ihn den Entwurf generieren und prueft dann kritisch. Der Lernwert liegt im Pruefen: Deckt der Plan alle Akzeptanzkriterien ab? Ist die Testpyramide beachtet (Unit-Basis, schmale ITs, minimal E2E)? Der Plan us-7 ist die Referenz fuer Detailtiefe.
Übung 4 · Vertikale Schicht

Eine Story umsetzen

Ziel: den vollen Fluss durchlaufen — Domain bis Test, unter allen Guardrails.

  1. Nimm deinen Plan aus Übung 3.
  2. Domain zuerst: Aggregat/VO als immutable record in domain/model/.
  3. Port in/ + out/, dann Application Service.
  4. Adapter: Panache-Repository + REST-Resource + DTOs.
  5. Liquibase-Migration + Include in changeLog.xml.

Tests (Pyramide!)

✓Unit: Domain-Invarianten + Service mit gemocktem Port
✓@QuarkusTest-IT gegen REST
✓.feature mit exakt so vielen Szenarien wie die Story

Abschluss: ./mvnw verify grün + passenden Reviewer-Agenten laufen lassen.

Die Koenigsuebung — realistisch 20-30 Minuten, ggf. als Paar oder als gefuehrte Live-Session. Reihenfolge betonen: immer Domain zuerst (nach innen), Adapter zuletzt. Wer /implement nutzt, laesst den Skill die Struktur anlegen und review-t das Ergebnis. Nicht die Pyramide vergessen: die Basis sind Unit-Tests, E2E bleibt schmal.
Übung 5 · Bonus

ADR & End-to-End

Architekturentscheid festhalten

  1. Triff eine bewusste Entscheidung (z. B. Fallnummern-Format).
  2. Lege specs/adr/adr-<NN>-<slug>.md an: Kontext → Entscheidung → Begründung → Konsequenzen → Verworfene Alternativen.
  3. Ergänze Index & mkdocs.yml-Navigation.

E2E im Browser

  1. Schreibe ein @E2E-Feature für einen UI-Pfad.
  2. Führe npm run e2e:cucumber aus.
  3. Halte die Spitze der Pyramide schmal — nur kritische Pfade.

Denk an die Sprache: Umlaute in allem Lesbaren, ASCII-Transliteration nur in Identifiern (Enums, Tags, Slugs).

Puffer-Uebung fuer Schnelle. Der ADR-Teil zeigt, dass auch Architekturentscheide zur nachvollziehbaren Spur gehoeren (Skill /adr automatisiert das). Beim E2E-Teil die Pyramide-Botschaft wiederholen: Playwright ist langsam und bruechig, also nur kritische Pfade. Alles Testbare gehoert auf eine tiefere Ebene.
